# Maintenance lessons

Record conditions, corrections, and evidence limits; command details remain with the owning Skill.

| Condition | Maintained correction |
|---|---|
| Live source links follow working changes | Use unmounted worktrees for risky work; tags and observed hashes are not runtime locks. |
| Resolving a script path loses consumer sibling tools | Inspect the consumer projection when finding optional integrations; distinguish it from the canonical Skill source. |
| A directory exists but the harness cannot see the Skill | Verify native discovery, then execution and actual production separately. Avoid duplicate mounts as a speculative repair. |
| Persona, experience, or promotion defaults leak into content | Separate explicit brief switches and verified facts from distribution identity and channel bylines. |
| Lower-level checks are reported as complete delivery | Record files, rendering, platform drafts, phone review, and publication independently. |
| A reviewer invents state requirements | Cite the actual contract; distinguish violations, contract gaps, and preferences. Preserve original and corrected assessments. |
| Article state and series summaries drift | Treat packages as fact and summaries as projections; update only uniquely matched projections. |
| Credential hardening discards valid device locators | Keep credentials device-owned; migrate complete pairs explicitly, verify new locators, and retain old entries until removal is authorized. |
| A natural Chinese single-source disclosure was rejected | Recognize “只有一份来源” as well as existing phrasing; retain the independent production failure and deterministic regression evidence. |

Single-stage corrections belong in its reference/tests; project business decisions stay with that project. Vendor-specific maintenance stays with that vendor. An old passed run does not establish current support.
